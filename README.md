# ANVAYA

> Sanskrit: *connection, lineage* — Engineering Knowledge Graph & Evidence-Backed Agent on **FalkorDB**.

Anvaya constructs an operational knowledge graph of repository lineage directly from Git history, unlocking deterministic multi-hop reasoning: who knows code, change risk, why changes occurred, who should review pull requests, and human-approved action lifecycles.

---

## What Anvaya Does

Anvaya transforms software repositories into an operational knowledge graph on **FalkorDB**. Rather than feeding raw source code into an ungrounded LLM or relying on fuzzy vector embeddings, Anvaya executes multi-hop graph traversals across commit history, file co-changes, and organizational memory to solve core engineering coordination challenges:

```text
User Question
      ↓
Agent Intent Understanding & Tool Routing
      ↓
FalkorDB Multi-Hop Graph Traversal
(:File)-[:CO_CHANGES]-(:File)<-[:TOUCHES]-(:Commit)<-[:AUTHORED]-(:Person)
      ↓
Deterministic Evidence Verification (EvidenceVerifier)
      ↓
Verified Narration & Structured Context
      ↓
Proposed Action (request_review)
      ↓
Human Approval Gate (Mandatory)
      ↓
Execution & Graph Provenance ((:Action)-[:RESULTED_IN]->(:Outcome))
      ↓
Persistent Graph Memory ((:Constraint))
      ↓
Fresh Session → Changed Future Recommendation
```

---

## Why FalkorDB is Central

FalkorDB is the foundational, indispensable operational core of Anvaya. Anvaya cannot provide its core reasoning workflow if FalkorDB is removed:

1. **Persistent Relationship Representation**: Code relationships (directory structures, file containment, module hierarchies, and authorship history) are natively expressed as graph topologies rather than flat relational tables or ungrounded vector spaces.
2. **Bounded Multi-Hop Graph Traversal**: FalkorDB executes multi-hop Cypher traversals in single-digit to tens-of-milliseconds (typically 5 ms – 35 ms for graph queries, 40 ms – 150 ms for full agent workflows), traversing `File → CO_CHANGES → File ← TOUCHES ← Commit ← AUTHORED ← Person`.
3. **Multi-Hop Impact-to-Reviewer Reasoning**: Reviewer routing and change blast-radius are derived directly through graph connectivity, combining direct file touches with statistical co-change clusters.
4. **Evidence Lineage**: Every claim generated by the agent links directly to an immutable graph node or relationship ID (`ev_commit_*`, `ev_cochange_*`, `ev_constraint_*`) verifiable by `EvidenceVerifier`.
5. **Persistent Graph Memory**: Organizational memory constraints (e.g., reviewer unavailability established during human action rejection) are stored directly as `(:Constraint)` nodes in FalkorDB, surviving process restarts and changing future agent decisions.
6. **Action Provenance**: Approved actions transition through a strict state machine and write immutable `(:Action)-[:RESULTED_IN]->(:Outcome)` audit nodes into the graph.
7. **Fail-Closed Graph Dependency**: If FalkorDB is offline or unreachable, Anvaya fails closed immediately (`refused=True`, `reason_code=NO_PATH` or HTTP 503). It refuses to hallucinate when graph evidence is unavailable.

## Graph Model & Repository Scoping
 
Anvaya models software development as a typed, property-rich, repository-scoped knowledge graph in FalkorDB:
 
```text
Repository
  ├── CONTAINS → File
  ├── HAS_COMMIT → Commit
  └── SNAPSHOT → Sync

Person
  └── AUTHORED → Commit

Commit
  └── TOUCHES → File (with added, deleted)

File
  ├── IN_MODULE → Module
  └── CO_CHANGES → File (with count, last_ts)

Action
  └── RESULTED_IN → Outcome

Constraint
  └── APPLIES_TO → Person
```

### Nodes & Repository Identity
- `(:Repository {name: str})` — Target repository root.
- `(:File {repo: str, path: str})` — Source file node, uniquely identified by compound key `{repo, path}` to prevent cross-repository collision.
- `(:Module {repo: str, path: str})` — Directory subsystem node, scoped by `{repo, path}`.
- `(:Commit {sha: str, ts: str, subject: str, repo: str})` — Git commit snapshot with repository tag.
- `(:Person {name: str, email: str, login: str})` — Contributor identity.
- `(:Sync {id: str, head_sha: str, synced_at: str, commit_count: int, source: str})` — Freshness tracking snapshot.
- `(:Action {id: str, type: str, status: str, reviewer: str, target: str, repo: str})` — Proposed/approved engineering action.
- `(:Outcome {id: str, status: str, success: bool, created_at: str})` — Sandbox execution result.
- `(:Constraint {id: str, type: str, subject: str, scope: str, active: bool})` — Persistent memory exclusion constraint.

### Relationships
- `(:Repository)-[:CONTAINS]->(:File)`: Repository file containment.
- `(:Repository)-[:HAS_COMMIT]->(:Commit)`: Repository commit lineage.
- `(:Repository)-[:SNAPSHOT]->(:Sync)`: Ingestion snapshot and freshness provenance.
- `(:File)-[:IN_MODULE]->(:Module)`: Module and directory tree containment.
- `(:Commit)-[:TOUCHES {added: int, deleted: int}]->(:File)`: Granular commit modifications and line churn per file.
- `(:Person)-[:AUTHORED]->(:Commit)`: Contributor commit authorship.
- `(:File)-[:CO_CHANGES {count: int, last_ts: str}]->(:File)`: Historical co-change coupling between files within the same repository.
- `(:Action)-[:RESULTED_IN]->(:Outcome)`: Sandbox action execution audit trail.
- `(:Constraint)-[:APPLIES_TO]->(:Person)`: Persistent organizational memory constraint excluding specific reviewers.

## Important Cypher Operations in Anvaya

Anvaya executes specific, deterministic Cypher operations in FalkorDB across its tools:

1. **Reviewer Identification & Recency Ranking** (`reviewers_for`):
   ```cypher
   MATCH (f:File {repo: $repo_name, path: $target_path})
   MATCH (p:Person)-[:AUTHORED]->(c:Commit)-[t:TOUCHES]->(f)
   WHERE NOT (p.email IN $exclude_emails)
   WITH p, count(DISTINCT c) AS commit_count, sum(t.added) AS lines_added,
        sum(t.deleted) AS lines_deleted, collect(c.sha) AS all_shas, collect(c.ts) AS all_ts
   RETURN p.name, p.email, commit_count, lines_added, lines_deleted,
          all_ts[0] AS last_commit_at, all_shas[0] AS last_commit_sha, all_shas AS evidence_commits
   ORDER BY commit_count DESC, lines_added + lines_deleted DESC, last_commit_at DESC
   LIMIT $limit
   ```

2. **Blast-Radius Co-Change Extraction** (`change_impact`):
   ```cypher
   MATCH (f:File {repo: $repo_name, path: $target_path})-[cc:CO_CHANGES]-(other:File {repo: $repo_name})
   RETURN other.path AS other_path, cc.count AS count, cc.last_ts AS last_ts
   ORDER BY count DESC, last_ts DESC
   LIMIT $limit
   ```

3. **Multi-Hop Impacted Reviewers Traversal** (`impact_reviewers`):
   ```cypher
   MATCH (p:Person)-[:AUTHORED]->(c:Commit)-[t:TOUCHES]->(f:File {repo: $repo_name})
   WHERE f.path IN $all_paths
   RETURN p.name AS person_name, p.email AS person_email, f.path AS file_path,
          count(DISTINCT c) AS c_count, collect(DISTINCT c.sha)[0..10] AS shas, max(c.ts) AS last_ts
   ```

4. **Persistent Memory Constraint Enforcement** (`MemoryService`):
   ```cypher
   MATCH (c:Constraint {active: true, type: 'reviewer_unavailable'})
   WHERE c.scope = $scope OR c.scope = $raw_scope
   RETURN c.id, c.subject, c.scope, c.source_action_id
   ```

5. **Action Provenance & Outcome Logging** (`ActionService`):
   ```cypher
   MERGE (a:Action {id: $action_id})
   MERGE (o:Outcome {id: $outcome_id})
   ON CREATE SET o.status = $status, o.success = $success, o.created_at = $created_at, o.output = $output
   MERGE (a)-[:RESULTED_IN]->(o)
   ```

## Agent Workflow

Anvaya enforces a strict operational separation between orchestrators and source-of-truth knowledge:

```text
1. USER REQUEST
   "I'm going to modify databases/backends/postgres.py. What could this affect, who should review it, and why?"
        ↓
2. DETERMINISTIC TOOL ROUTING
   Agent extracts parameters -> selects 'impact_reviewers' tool from ToolRegistry.
        ↓
3. MULTI-HOP GRAPH INVESTIGATION
   FalkorDB traverses:
   postgres.py --[:CO_CHANGES]--> mysql.py --[:TOUCHED_BY]--> Commit --[:AUTHORED]--> Person
        ↓
4. EVIDENCE VERIFICATION
   EvidenceVerifier checks 100% of claims against attached Evidence records.
        ↓
5. VERIFIED NARRATION
   Factual explanation generated strictly from verified claims without hallucinated confidence scores.
        ↓
6. ACTION PROPOSAL
   Creates request_review action with status PROPOSED (human approval required).
        ↓
7. HUMAN DECISION
   Human reviews proposal -> approves or rejects with reason.
        ↓
8. SANDBOX EXECUTION & MEMORY
   - If approved: executes notification and writes (:Action)-[:RESULTED_IN]->(:Outcome) to FalkorDB.
   - If rejected as unavailable: writes (:Constraint {type: 'reviewer_unavailable'}) to FalkorDB.
```

## Context Packages

> **Disclaimer**: *A Context Package is not a replacement for source code. It is a bounded relational context layer designed to reduce the amount of repository context an agent must reconstruct from scratch.*

Rather than dumping raw source files into an LLM context window, Anvaya synthesizes a bounded, machine-readable **Context Package** (`ContextPackage`) representing the structural, historical, and organizational reality of a repository or target subject:

- **Repository Context** (`subject_type: repository`): Architecture modules, file churn hotspots, core contributors, cross-module dependencies, and persistent constraints.
- **File Context** (`subject_type: file`): Module membership, author lineage, co-change blast radius, and recommended reviewers.
- **Module Context** (`subject_type: module`): Subsystem file containment, churn, and module-specific top authors.
- **Bounds Enforced**: Traversal depth is clamped to `[1, 5]`. Results exceeding file or contributor limits set `truncated=True` with explicit `truncation_reason`.

## Persistent Memory

Anvaya's persistent memory directly addresses **Track 02 (Agent Memory and Coordination)**:

1. **State Surviving Process Restarts**: Constraints are persisted as graph nodes in FalkorDB, not stored in ephemeral process memory.
2. **Changed Future Decisions**:
   - **Session 1**: User asks who should review `postgres.py`. Anvaya recommends **Tom Christie** (#1 by historical commits).
   - **Human Decision**: User rejects Tom Christie with reason *"Reviewer on sabbatical / unavailable"*. FalkorDB records a `reviewer_unavailable` constraint.
   - **Session 2 (Fresh Process)**: The exact same question is asked in a new session. Anvaya discovers the active constraint in FalkorDB, excludes Tom Christie, and elevates **George Bogodukhov** to #1!

## Human Approval & Sandbox Execution

Autonomous AI agents must not make unverified external repository mutations without explicit human authorization:

- **State Machine**: `PROPOSED -> APPROVED -> EXECUTING -> SUCCEEDED` (or `REJECTED`).
- **Strict Enforcement**: Attempting to execute an action in `PROPOSED` state triggers `InvalidStateTransitionError: Human approval is mandatory before action execution`.
- **Sandbox Action Execution**: Approved actions are executed via `SandboxActionExecutor` (`backend/app/actions/executor.py`), which simulates external notifications without requiring write-scoped GitHub tokens. This safely demonstrates action lifecycle execution and provenance without risking destructive mutations on external repositories.
- **Audit Provenance**: Every approved execution writes an `(:Outcome)` node directly linked to `(:Action)` in FalkorDB with execution timestamp, status, and sandbox output.

## Refusal & Security Boundaries

Trust requires knowing when to refuse rather than hallucinating:

- **First-Class UI Refusal States**:
  - `NO_PATH`: Target file or module does not exist in graph lineage.
  - `LOW_EVIDENCE`: Insufficient historical commits or co-changes to justify an action.
  - `STALE_DATA`: Graph snapshot exceeds staleness window.
  - `OUT_OF_SCOPE`: Malicious prompt injection or arbitrary Cypher attempts.
- **Fail-Closed Kill Switch**: If FalkorDB connection health fails or raises an error, all tool endpoints fail closed immediately with structured refusals (`NO_PATH` / `503`).
- **Parameterized Cypher Execution**: Cypher inputs are parameterized and adversarial injection tests are included; user input is never concatenated into query strings.
- **Path Confinement**: Ingestion endpoints restrict file system paths to the configured `data/repos/` root via realpath normalization, preventing directory traversal.
- **Graph Name Confinement**: API requests cannot target arbitrary or non-canonical graph namespaces.

- Git

```bash
docker compose up -d
```

```bash
# Windows PowerShell / Bash:
mkdir -p data/repos
git clone https://github.com/Chandradeep05/ARTH.git data/repos/arth
git clone https://github.com/encode/databases.git data/repos/databases
```

Populate the canonical `anvaya` production graph using the provided ingestion script:
```bash
python scripts/ingest_sample_data.py
```

```bash
pytest backend/tests -v
```

### 7. Launch the Application
```bash
uvicorn app.main:app --app-dir backend --reload --port 8000
```
Open **`http://localhost:8000/`** in your browser to access the Anvaya engineering product surface!

## Production Deployment Guide (Vercel + Render + FalkorDB)

Anvaya is architected for decoupled cloud deployment:

```text
Browser / Client
      │
      ▼ (HTTPS)
Vercel Edge Proxy / Frontend
  - index.html, style.css, app.js, Cytoscape.js
  - vercel.json rewrites (/health, /api/*)
      │
      ▼ (HTTPS / REST)
Render Web Service (FastAPI)
  - uvicorn app.main:app
  - CORSMiddleware enabled
  - Strict parameterization & fail-closed boundaries
      │
      ▼ (Redis Protocol / TLS, port 6379)
FalkorDB Instance (Primary Graph Database)
  - FalkorDB Cloud or self-hosted persistent instance
  - Canonical graph: 'anvaya'
```

### 1. FalkorDB Setup & Persistence

Anvaya requires a reachable FalkorDB instance:
- **FalkorDB Cloud (Recommended)**: Create a free database at [cloud.falkordb.com](https://cloud.falkordb.com/).
  Provides a persistent managed endpoint with hostname, port, and password.
- **Self-Hosted Docker**: `docker compose up -d` (uses `falkordb/falkordb:latest` or pinned tag).
  > **Persistence Note**: In Docker, ensure a persistent host volume or Docker named volume is mounted to preserve graph memory across restarts. Ephemeral container filesystems will reset constraints upon container recreation.

### 2. Render Backend Deployment

1. Create a new **Web Service** on [Render](https://render.com/) pointing to your GitHub repository.
2. Configure settings:
   - **Environment**: `Python 3`
   - **Build Command**: `pip install -r backend/requirements.txt`
   - **Start Command**: `uvicorn app.main:app --app-dir backend --host 0.0.0.0 --port $PORT`
   - **Health Check Path**: `/health`
3. Configure Environment Variables on Render:
   - `PYTHONPATH`: `backend`
   - `APP_ENV`: `production`
   - `PORT`: (Provided automatically by Render)
   - `CORS_ORIGINS`: `https://your-app.vercel.app` (or comma-separated list of permitted origins)
   - `FALKORDB_HOST`: Hostname of your FalkorDB instance (e.g. `db-xxxx.cloud.falkordb.com`)
   - `FALKORDB_PORT`: Port of your FalkorDB instance (default `6379`)
   - `FALKORDB_USERNAME`: (Optional, e.g. `default`)
   - `FALKORDB_PASSWORD`: (Your FalkorDB password)
   - `FALKORDB_GRAPH_NAME`: `anvaya`
   - `FALKORDB_SSL`: `true` if your provider uses TLS/SSL, otherwise `false`

*(Alternatively, deploy automatically using the included `render.yaml` Blueprint).*

### 3. Vercel Frontend Deployment

1. Create a new project on [Vercel](https://vercel.com/) importing your repository.
2. In `vercel.json`, ensure the rewrites point to your deployed Render URL:
   ```json
   {
     "rewrites": [
       { "source": "/health", "destination": "https://your-render-service.onrender.com/health" },
       { "source": "/api/:path*", "destination": "https://your-render-service.onrender.com/api/:path*" },
       { "source": "/static/:path*", "destination": "/backend/app/static/:path*" },
       { "source": "/(.*)", "destination": "/backend/app/static/$1" }
     ]
   }
   ```
3. Deploy. The browser interacts solely through Vercel's edge proxy or your configured backend URL; FalkorDB credentials remain strictly server-side.

### 6. FalkorDB Connection Diagnostics

Anvaya includes safe, categorized diagnostics (`/health` returns HTTP 503 with structured details when unreachable without exposing credentials):

| Error Category | Root Cause | Remediation |
| :--- | :--- | :--- |
| `dns_resolution_failed` | Host name cannot be resolved | Verify `FALKORDB_HOST` spelling and public DNS reachability |
| `tcp_connection_refused` | Connection rejected on port | Ensure FalkorDB is running and firewall allows traffic on port `6379` |
| `authentication_failed` | Incorrect credentials | Verify `FALKORDB_USERNAME` and `FALKORDB_PASSWORD` |
| `tls_ssl_handshake_failed` | TLS certificate or SSL mismatch | Check `FALKORDB_SSL` setting (`true` vs `false`) |
| `connection_timeout` | Network packet drop or firewall | Verify security groups and provider network access lists |
| `graph_not_found` | Graph has not been initialized | Run `python scripts/ingest_sample_data.py` to seed graph |

## Known Limitations

- **Git-Only Lineage**: Architecture and coupling are derived strictly from Git directory trees, commit touches, and historical co-change co-occurrence. Dynamic runtime microservice calls, reflection, and network topologies are not modeled.
- **Historical Probability**: Blast-radius co-changes reflect statistical commit coupling, not abstract syntax tree (AST) execution paths.
- **Bounded Window**: Historical depth is intentionally bounded to avoid graph explosion on very large enterprise monorepos.
- **Sandbox Action Execution**: Review request actions are executed and provenanced in FalkorDB within a simulated sandbox environment (`sandbox: true`); live automated mutation of external GitHub pull-request review assignments is intentionally decoupled to ensure human oversight.
- **Local Benchmark Measurements**: Graph query latencies (typically 9.8 ms – 65 ms on local benchmarks) reflect local FalkorDB execution. In our local benchmark, graph-backed reviewer retrieval (`reviewers_for`) completed in **9.83 ms** (approx. 34× faster than parsing raw Git history at **333.61 ms**). Latencies vary by repository size, traversal depth, and host hardware.
